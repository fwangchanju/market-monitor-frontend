# 작업 진행 프로세스

- 실제 변경 전에는 무엇을, 어떻게 할지 설명한다. 사용자가 검토하거나 질문하면 답하고 결정된 방향으로 진행한다.
- PR 승인·병합과 GitHub Actions 실행·재실행·배포는 별도 확인 요청 없이 진행할 수 있다. 운영 서버에서 직접 배포하지 않는다.
- commit/push를 진행할 때는 현재 브랜치에 열려 있는 PR이 있는지 먼저 확인한다. 있다면 기존 PR에 변경을 반영한다. 별도 PR이 필요한 작업은 새 브랜치에서 진행한다.
- 열려 있는 PR이 없다면, 곧바로 새 브랜치를 만들지 말고 먼저 현재 브랜치가 이미 main에 머지됐는지 확인한다(`git merge-base --is-ancestor <현재 브랜치 HEAD> origin/main`, 또는 GitHub에서 해당 브랜치를 head로 하는 closed/merged PR 이력 조회). 이미 머지된 게 확인되면 그 브랜치는 낡은(stale) 브랜치일 뿐이므로 안심하고 main 기준 새 브랜치를 만들면 된다.
- 머지 이력도 없고 열려 있는 PR도 없다면(즉 커밋만 push되고 PR이 없는 상태), 그 커밋이 누락되지 않도록 현재 브랜치에서 PR을 만든다.

## 단계별로 나누어 진행하는 대규모 기능 작업

- 그날 작업하기로 한 내용 중 가장 대표적인(혹은 분량이 가장 많은) 주제를 기준으로 브랜치명을 정한다. 프론트/백엔드는 각자 독립적으로 브랜치명을 정하며 서로 맞출 필요는 없다. 해당 브랜치로 그날 작업한 커밋 전체를 하나의 PR로 main에 병합한다. 각 단계는 하나의 커밋으로 남긴다.
- 각 단계를 시작하기 전에, 해당 단계의 세부 작업 목록과 세부 작업별 간략한 진행 계획을 제시한다.
- 세부 작업은 한 번에 하나씩 진행한다. 하나를 완료하면 다음 세부 작업으로 넘어간다.
- 파일 수정 후 빌드/테스트(백엔드 컴파일/테스트, 프론트 린트/빌드/테스트 등) 실행은 기본 동작이 아니다. 다음 세 경우에만 실행한다: (1) 사용자가 명시적으로 요청했을 때, (2) 커밋하기 직전, (3) 계획된 세부 작업 하나가 전부 끝나서 다음 세부 작업으로 넘어가기 전. 그 외 모든 수정(사용자가 코드를 보면서 그 자리에서 요청하는 리팩터링·네이밍 변경·연산자 교체 등)은 수정만 하고 결과(코드)를 보여준 뒤 멈춘다. "이 정도는 확인해봐야지"라고 스스로 판단해서 끼워넣지 않는다.
- 한 단계의 모든 세부 작업이 끝나면 그 단계 전체를 하나의 커밋으로 묶는다.
- 커밋 후에는 곧바로 다음 단계의 세부 작업 목록 및 계획을 제시하고, 위 과정을 반복한다.
